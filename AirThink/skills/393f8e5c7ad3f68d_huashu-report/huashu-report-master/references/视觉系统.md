# 视觉系统

规范来自 41 份 PDF 的字体、字号、颜色、版式实测。数字是统计结果，不是审美主张。样本与局限见 `实证基线.md`。

## 版式

| | 尺寸 | 用在 |
|---|---|---|
| 竖版 A4/Letter | 595×842 / 612×792 pt | 35/41 份。学术、调查、研报、政策 |
| 横版 16:9 | 960×540 pt | deck 型。BCG、Deloitte、ICONIQ、KPMG |

**默认竖版。** 只有当报告的使用场景确实是「投影出来讲」时才用横版。做成横版的报告在手机和 A4 打印上都难读——这是为了会议室牺牲了所有其他场景。

栏数：
- 单栏窄版心（版心约占页宽 65%）——OpenAI、学术型。留白多，适合长段落论述
- 双栏——Reuters DNR、多数调查报告。适合文字量大且要嵌小图
- 左文右图固定分栏（文字栏约 1/3）——Deloitte、deck 型

## 配色

**这是实测中最反直觉的一条：正文主色 98%（40/41）是近黑；正文里的品牌色中位只占 2.8% 字符，最高 8%。**

| 报告 | 正文主色 | 占比 | 品牌色占比 |
|---|---|---|---|
| PwC Jobs Barometer | #000000 | 99% | 橙 #fd5108 < 1% |
| Anthropic Cadences | #231f20 | 94% | 蓝 #00558b 3% |
| Reuters DNR | #3c3c3b | 88% | 深蓝 #0e2050 5% |
| Stanford Canaries | #000000 | 95% | 品红 #ec008c < 1% |
| CSET | #30353a | 92% | 蓝 #003da6 6% |

结论：**品牌色是稀缺资源。** 它出现在图表数据、章节标记、强调数字上，不出现在正文里。把正文染成品牌色是外行做法——它同时降低可读性和品牌辨识度（到处都是等于哪儿都不是）。

正文黑的具体选择：**不用纯黑 #000000 也很常见**（#231f20 暖黑、#30353a 冷黑、#3c3c3b 中性灰黑）。纯黑在铜版纸和屏幕上都偏硬，专业报告多用近黑。

只有一个例外：KPMG 用品牌深蓝 #00338d 做正文（77%）。这是整套设计围绕单一品牌色重建的结果，不是随手改的，不要模仿一半。

配色规模：
- 分类色：**不超过 6 个**。超过就该换图型，不是加颜色。
- 语义色：增/减、好/坏用两端色（绿↔棕、蓝↔橙），中间用中性灰
- 高亮：一个报告只留一个高亮色，用在「这就是重点」的地方

## 字号

英文报告实测正文集中在 **8–10 pt**（高频档：8 / 8.5 / 9 / 10 / 11 / 12 pt）。

**中文报告在此基础上整体上浮。** 42 份样本几乎全是英文报告；汉字笔画密度高、
无词间空格，同字号下中文比英文显小且更挤。一份实际交付的中文报告正文 9.4pt、
图注 6.7pt，被读者反馈明显偏小——这是踩过的坑，不是理论推演。

层级基线（A4 竖版中文）：
```
章节大标题   22–28 pt  粗
页面标题     13–16 pt  粗
图表标题     10.5–11.5 pt  粗
正文          10–10.5 pt  常规（下限 9.8，不做 9pt 中文正文）
表格          8.8–9.5 pt
图注/数据源   7.5–8 pt（下限 7.2）
页眉页脚      6.5–7 pt  浅灰
```

deck 型整体上浮 2–4pt（正文 11–12pt，结论句标题 20–26pt）。英文报告可回落到实测档。

**字号跨度要够。** 正文 10pt 配标题 11pt 是最常见的业余感来源——层级之间至少 1.3 倍。

## 行距

字号只解决「看得清」，行距解决「读得顺」。中文正文行距不足是仅次于字号偏小的密度问题：

```
中文正文     1.68–1.78（10pt 正文配 1.72 是安全值）
英文正文     1.45–1.6
标题         1.2–1.35（多行大标题取下限）
表格单元格   1.5–1.6
图注/数据源  1.45–1.55
deck 大字    1.15–1.3
```

- 行距与版心宽度联动：单栏窄版心（65%）可取下限，双栏窄列取上限——列越窄换行越频繁，行距不足时视线容易串行
- 段落间距 0.5–0.8em，与首行缩进二选一，不叠加
- 正文加 `orphans: 2; widows: 2`，段落首尾行不孤立在页边

这些值写在 `assets/base.css` 的变量里，改变量不要散写在各选择器上——散写正是行距在一份报告里从 1.5 漂到 1.9 的原因。

## 字体

实测出现最多的家族：机构自有字体（OpenAISans、HendersonBCGSans、ICONIQQuadraat）、Helvetica Neue LT Pro、Tisa Sans Pro、Nunito Sans、Franklin Gothic、Univers。

规律：
- **无衬线做 deck 和企业报告，衬线做学术和调查报告**
- 有品牌字体就全程用品牌字体，一份报告最多两个家族（一个标题一个正文）
- 数字用**表格数字（tabular figures）**，让上下行的数字对齐。这是表格看起来专业与否的分水岭

中文报告的落地字体栈（macOS/Chromium 渲染实测可用，写进 CSS 直接用）：

```css
/* 无衬线（企业报告 / deck）*/
font-family: 'Helvetica Neue','PingFang SC','Source Han Sans SC',sans-serif;
/* 衬线（学术 / 调查）*/
font-family: 'Times New Roman','Songti SC','Source Han Serif SC',serif;
```

两条容易做错的：
- **西文字体放在中文字体前面**——数字和英文走西文字形，比 CJK 字体自带的拉丁字形精神得多；反过来排数字会发虚
- 表格数字用 `font-variant-numeric: tabular-nums` 声明在表格和图表标签上；PingFang 自身不带 tnum，西文字体前置后数字由 Helvetica Neue 承担，这条才生效
- 中文没有斜体传统，强调用字重或颜色，不用 `font-style: italic`（渲染出来是机械倾斜）

### 标题与正文不必同一个家族

上面那条「无衬线做企业报告、衬线做学术」说的是整体倾向，不是二选一。
第三种组合存在，而且是财经数据版的标配：

| 组合 | 标题 | 正文与数据 | 用在 |
|---|---|---|---|
| 全无衬线 | 无衬线 | 无衬线 | 企业报告、deck |
| 全衬线 | 衬线 | 衬线 | 学术、调查 |
| **双轨** | **衬线** | **无衬线** | 财经数据版、杂志专题、一页一图的数据卡片 |

双轨那条有一条硬边界：**衬线只做到标题为止。** 一旦进入表格、图表、坐标轴、
数值标签，立刻换无衬线。晚点小数据的卡片上，大标题和副标题是宋体，
而同一张卡片上的 `538.74`、`7999 / 8999`、轴上的 `5S / 6 / 6S` 全是无衬线。
标题的衬线负责给版式定调，数据的无衬线负责让数字等宽可扫。
**把数字也做成衬线是这套里最常见的做错方式**——衬线数字笔画有粗细变化，
一列排下来参差感比比例数字还重。

`base.css` 里 `--font-head` 与 `--font-body` 是两个独立变量，双轨就是把
`--font-head` 赋给 `--font-serif`、`--font-body` 保持 `--font-sans`。

## 封面

实测的六种范式，以及一条规律：**封面设计强度与「谁付钱读」成反比**。

| 类型 | 做法 | 例子 |
|---|---|---|
| 抽象数据图形 | 线框地形、粒子环、雷达 | ICONIQ、Reuters、BCG |
| 品牌几何 + 实拍 | 品牌色块压在办公照片上 | PwC |
| 全黑 + 品牌光效 | 黑底、荧光品牌色、粗体白字 | BCG |
| 浅色渐变 + 3D 品牌图形 | 彩色丝带、流线 | Deloitte |
| 深色 + 数据粒子 + 双 logo | 机构联名 | Reuters × Oxford |
| 纯文字 | 标题+作者+摘要，零装饰 | Stanford、arXiv 系 |

要卖服务的（VC/咨询/投行）封面重设计；要被引用的（大学/智库）封面就是元数据。**先想清楚你是哪一种**，再选封面方向。

封面必须有的四件：标题、副标题（一句话说清是什么）、机构 logo、日期（精确到月）。deck 型加保密标记。

## 表格排版

数据表是报告里最容易翻车的组件，而且翻的方式很隐蔽——它不会报错，只会让读者读到错的东西。

**列必须有可见边界。** 相邻两列一个右对齐、一个左对齐时，内容会在列缝处贴死，
读者看到的不是两列数据，是一句连起来的假句子：

```
84%尚未围绕 AI 能力重新设计岗位或工作性     ← 数值列 + 口径列糊成一句
调研）Deloitte State of AI in the         ← 样本量列 + 出处列糊成一句
```

靠加 padding 调不出来——列窄的时候 padding 会被内容挤掉。可靠做法：

| 做法 | 为什么 |
|---|---|
| 列之间加 .5px 浅色竖分隔线 | 唯一可靠地告诉眼睛「这里是列边界」的手段 |
| `table-layout: fixed` + `overflow-wrap: anywhere` | 长内容换行而不是撑破列宽 |
| 单元格左对齐，**不要两端对齐** | 两端对齐让行尾顶到列边界，加剧粘连 |
| 混排数据表里数值列**不要右对齐** | 右对齐把内容推到列右边界，正好贴上下一列起点 |
| 水平 padding 给到 3mm 以上 | 分隔线之外还需要真实的 gutter |

数值右对齐只在**纯数字表**（财务报表那种要对齐小数点的）里成立。
数字与长文本混排的表里，右对齐是纯粹的负债。

**但最后一段要补一句**：上面这条针对的是**中间列**。**最后一列右对齐是安全且推荐的**——
它右边没有邻居可贴，反而顺手给倒数第二列制造了一个对齐反差。
晚点小数据的产品表（左栏机型、中栏内存类型、右栏容量）右栏就是右对齐的。

### 无竖线表格：成立条件比看上去严

上面那组做法里，竖线是**最省心的解**，不是唯一的解。财经数据版式
（晚点小数据、Reuters 图表、Bloomberg Businessweek）一条竖线都不用：
表头下一条规则线，行间发丝线，列边界全靠留白和对齐反差。

它成立，是因为同时满足三个条件——少一个就退回粘连：

1. **每格内容短。** 列宽由内容决定，不由最长的那条文本决定。卡片列里放的是
   `LPDDR5X`、`12 GB`、`2026E` 这种字串，不是「调研）Deloitte State of AI in the」。
2. **列间 gutter 写进 token，不靠内容撑。** 实测 `晚点` 那张产品表，两条净空分别是
   表宽的 42% 和 39%（≈ 15.7 个字宽）。这个量级意味着**一页只放得下两三列**——
   它是「一页一图」介质的产物，不是任何表格都能套的默认值。
3. **相邻列的对齐方式不同。** 左对齐紧挨右对齐，是比竖线更强的边界信号——
   眼睛在对齐线上找边界，不在线上找。

判据一句话：**这张表里最长的那条内容，会把列撑到贴死吗？**
会 → 用竖线。不会（内容是短标签、短数值、日期、型号）→ 无竖线版更干净。

无竖线版的两个配套动作（实测来的，和我原来的猜法不一样）：

- **表头只加粗，不抬字号、不加底色。** `晚点` 的表头「产品」与正文墨高同为 49px，
  区别全在字重。
- **表头下那条线不比行间线重。** 实测两处最深灰度同为 217（同一条发丝线）。
  表头带是靠**字重**立住的，不是靠更重的线。想改成两档线也成立
  （`base.css` 现在就是 `.7pt 近黑` 配 `.4pt 浅灰`），但那是另一种做法，别说是同一种。
- **表尾不收线。** 最后一行下面没有线——表格的底由留白宣布，不由框线宣布。

行高也别照搬：`晚点` 的单行行高 195px ÷ 字号 55px ≈ **3.55 倍字号**；
`base.css` 报表表的现值 ≈ 2.7 倍。差得不算多，但方向是一致的——
**卡片是「一页一图」的介质，报告是「一页多组件」的介质**，
它的 42% 净空搬进 60 页报告，页数会翻倍。

**表格宽度分配要留余量。** `table-layout: fixed` 下列宽是硬的，
按最长内容估宽度再加 15% 余量，否则中文长词会被拆到下一行中间。

**行高与分页。** 数据表加 `page-break-inside: avoid`，
一张表被拆到两页且第二页没有表头，读者就没法读了。表本身超过一页时，
改用 `thead` 让表头在每页重复。

## 页眉页脚

竖版页眉的三种做法：
1. **面包屑定位**（AI Index）：`1.1 NOTABLE AI MODELS | RESEARCH AND DEVELOPMENT | AI INDEX REPORT 2026` —— 400 页报告的必需品，读者翻到任何一页都知道自己在哪
2. **报告名 + 机构 + 页码**（PwC）：最常见，够用
3. **只有章节名**（HF）：学术型的极简做法

页脚：页码必放。deck 型加 logo + 保密标记。

## 交付前的视觉自检

渲染成 PDF 后**逐页截图看**。以下四类错误只有看图才发现得了：

- **裁切**：图表右侧被版心边界切掉
- **溢出**：长标签撑破容器、表格超出页宽
- **坐标轴缩放**：Y 轴从非零开始把 3% 的差异画成 3 倍（除非明确标注并有理由）
- **空白区**：图表容器比内容大很多，页面下半空着

单文件 HTML 交付物额外注意：`file://` 协议下同源本地数据的 `fetch()` 会失败，数据要内联。
